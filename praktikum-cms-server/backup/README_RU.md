# «Практикум»: защищённый экспорт данных Valkey — ТОЛЬКО ТЕСТОВАЯ ВЕТКА

Дата подготовки: 31.10.2026. Код находится **только** в `staging/praktikum-safe-2026-10-30`. Рабочий Render и основной GitHub `main` не изменены.

## Что проверено

Отдельный защищённый маршрут `POST /backup/export`:

- **Выключен по умолчанию**: пока `ENABLE_BACKUP_EXPORT` не равен `true`, отвечает 404.
- При включении требует `X-Admin-Key` (существующий административный ключ) **и другой** `X-Backup-Key` (новый отдельный секрет длиной минимум 32 символа); идентичные ключи запрещены.
- Запрашивает пароль шифрования архива от 20 символов. Не помещайте его в код, URL, GitHub Actions, скриншоты или сообщения.
- Читает **только ключи `praktikum:*`** через Redis `SCAN`, `TYPE`, `PTTL` и бинарный `DUMP`; ключи вне этого пространства не читает.
- Создаёт архив JSON, зашифрованный AES-256-GCM с ключом scrypt. Содержимое ключей и сохранённый HTML передаются только как шифротекст по HTTPS.
- Контролирует число ключей (7 500), размер выгрузки (24 МиБ DUMP) и время обхода (90 секунд). Перед загрузкой ключа проверяет его объём через читающую команду `MEMORY USAGE`; если оценка больше 24 МиБ, DUMP не выполняется. Это дополнительная защита памяти, а не гарантия точного размера.
- Запрещает повторный экспорт чаще одного раза в 2 минуты в рамках процесса и параллельные экспорты.
- Возвращает `Cache-Control: private, no-store`. На диске сервера архив не создаётся.
- **Не сохраняет Redis на диск и не восстанавливает его автоматически; никакие записи в клиентскую БД не выполняются.**

В GitHub Actions изолированно проверены Redis 7.4 и **Valkey 8.1.10**, аналогичный рабочему по версии: авторизация, шифрование, повреждённый архив, чтение 1 210 тестовых ключей с множеством SCAN-страниц, исключение чужих ключей, восстановление в отдельную DB и совпадение счётчиков и HLL. **Последнюю версию проверяет отдельный CI: новые тесты защиты от слишком большого ключа и параллельной публикации дополняют проверку восстановления.**

## Что НЕ доказано и почему нельзя говорить «полная резервная копия»

- Экспорт `SCAN` **не атомарен**: новые события могут попадать в статистику во время обхода. Метаданные архива содержат `atomic:false`. Дополнительно версия публикации (`praktikum:published:updatedAt`) проверяется до и после обхода: при её изменении экспорт прекращается с ошибкой. Это защищает от смешивания двух редакций сайта, **но не делает снимок статистики атомарным**.
- Выгружаются только ключи `praktikum:*`, а не все ключи сервера Valkey. Это безопасно для общего хранилища, но не эквивалент полного RDB/AOF-дампа.
- Данные, которые уже были утрачены из `persistenceMode=off`, код вернуть не сможет.
- Нельзя гарантировать восстановление при смене Redis/Valkey и версий, пока **реальный** архив не проверен на целевой версии; искусственные DUMP/RESTORE внутри каждой версии успешно проверены.
- Важные данные, которые находятся вне `praktikum:*` или в других внешних системах, в экспорт не попадают.
- Нельзя проверить, есть ли на рабочей базе неучтённые ключи, только по опубликованному `GET /site` и `GET /stats`.
- Настоящий экспорт рабочего Valkey **ещё не выполнен**. Текущие инструменты Render дают метаданные сервиса, но не дают безопасного доступа к сырому содержимому Redis.

## Безопасный план получения реальных данных (без исполнения сейчас)

1. Сохранить действующую HTML-копию, код из `main`, GitHub-фиксацию и откат. Отдельно согласовать окно обновления, способ возврата к предыдущей версии и критерии успеха.
2. После отдельной проверки новой версии и разрешения владельца развернуть **строго проверенный** код через контролируемую процедуру. Не изменять `main` и не перезапускать Valkey до такого согласования. В действующем сервисе предусмотреть временный `BACKUP_EXPORT_KEY` (отдельный от `ADMIN_KEY`) и `ENABLE_BACKUP_EXPORT=true`, **только на время выгрузки**.
3. Запустить из **доверенного терминала**, не указывая секреты в параметрах команды:
   ```sh
   node praktikum-cms-server/backup/download-encrypted.cjs
   ```
   Утилита предлагает ввести административный ключ, отдельный ключ экспорта и пароль архива **с выключенным отображением символов**. Файл создаётся без перезаписи предыдущего, с ограничением прав в системах, где поддерживаются Unix-права; внутри сохраняется только зашифрованный JSON. Утилита сверяет наличие опубликованного HTML и метаданных публикации, сообщает об отсутствии важных ключей и выводит SHA-256 зашифрованного файла. Она обращается исключительно к заданному HTTPS endpoint на Render и не делает редиректов.
4. Проверить расшифровку, количество ключей, содержимое опубликованного HTML, метаданные публикации, диапазон и корректность статистики. Сделать ещё один снимок для оценки изменений при продолжающемся сборе событий, при необходимости согласовать остановку записи на время точного дампа.
5. Из другого чистого временного Valkey подходящей версии восстановить именно **реальный** зашифрованный архив, проверить типы, TTL, HTML, обе языковые версии, статистику и независимую CMS. **Никогда не выполнять RESTORE в рабочую базу.**
6. Сохранить архив и пароль **отдельно** в двух надёжных защищённых местах. Пароль не входит в архив; если он утерян, расшифровка невозможна.
7. Убрать `ENABLE_BACKUP_EXPORT=true` и временный ключ доступа, убедиться, что маршрут снова отвечает 404; проверить, что действующий сайт и админка работают и что аналитика не прервалась. Никакие изменения DNS, почты или тарифов Valkey не делать до подтверждённого восстановления.

## Восстановление зашифрованного архива в отдельный локальный Valkey

Подготовлен `backup/restore-isolated.cjs`. Он расшифровывает тот же архив `praktikum-redis-encrypted-v1` и разрешает `RESTORE` **только в пустой** `redis://127.0.0.1:6379/15`, с отдельной текстовой фразой подтверждения. Любое другое назначение, даже локальная DB14 или удалённый Redis, отклоняется до записи. Запрещены `FLUSHDB`, `DEL` и `REPLACE`; существующие ключи не перезаписываются.

Требования к безопасной локальной проверке:

1. Запустить отдельный временный Redis/Valkey на локальном компьютере или изолированном контейнере с портом `127.0.0.1:6379`. Убедиться, что это **не рабочая БД и что DB15 пуста**. Нельзя выполнять проверку на серверах, где DB15 содержит реальные данные.
2. Архив копировать только в защищённую папку с ограниченными правами. Пароль не вводить в параметры команды. Выполнить `node backup/restore-isolated.cjs /защищённый-путь/зашифрованный-архив.json` из папки `praktikum-cms-server` с установленными пакетами. Программа скрыто запросит пароль и фразу `RESTORE_TO_EMPTY_LOCAL_DB15_ONLY`.
3. Перед любыми записями программа проверяет целевой адрес, пустоту DB15, структуру архива, присутствие опубликованного HTML и даты публикации, размер, базовую кодировку, сроки TTL. Если ключ истёк, он пропускается; **если истекла страница или дата публикации, всё восстановление отклоняется до записи**.
4. После восстановления отдельно запустить CMS **с тестовыми секретами** на DB15 и сравнить её `GET /site`, `GET /meta`, `GET /stats` с настоящей контрольной записью. Только такой тест приближает нас к проверке реальной копии.
5. При любой ошибке после начала записи DB15 может быть **частично заполнена**; программа явно сообщает об этом, ничего не удаляет автоматически. Такую DB15 нельзя считать проверенной и нельзя подключать к публичному сайту.

Важно: программа не синхронизирует работающую базу, не переносит DNS и не подключает почту. Восстановление реальных клиентских ключей ещё **не проводилось**: оно возможно только после авторизованной выгрузки настоящего архива. В GitHub Actions это проверяется на искусственных ключах в одноразовой базе.

## Защита секретов и ограничения экспорта

- Клиентская выгрузка защищена как HTTPS **и** AES-GCM, но сервер CMS получает пароль во время запроса; не используйте скомпрометированный сервер.
- Пароль и ключи нельзя передавать в ChatGPT, в тикеты, в GitHub Issues или хранить в файлах репозитория.
- Возможная компрометация `ADMIN_KEY` вместе с `BACKUP_EXPORT_KEY` при включённом экспорте раскрывает возможность скачивания **зашифрованного** архива. Ключи должны быть независимыми и временными.
- `SCAN` по изменяемой базе — не транзакционная резервная копия. Для строгого снимка нужен согласованный контроль записи, нативное резервирование с постоянной записью или иной подтверждённый механизм.
- Не включайте функцию в интернете постоянно. Для будущей штатной работы предпочесть устойчивое хранилище и запланированное резервирование.

## Технические компоненты

- `backup-export.cjs` — read-only сборщик DUMP+PTTL и AES-256-GCM, также функция расшифровки для локальной проверки.
- `download-encrypted.cjs` — интерактивный скачиватель зашифрованного файла, **не активирует** серверный маршрут.
- `tests/integration-backup.cjs` — изолированный API + Redis/Valkey тест на временных DB14/DB15, только в GitHub Actions, без секретов клиента.
- `.github/workflows/praktikum-secure-export-qa.yml` — запускает тесты на Redis 7.4 и Valkey 8.1.10.

**Рабочий `main`, Render и текущий клиентский Valkey не изменены.**
