# Практикум — регламент безопасной эксплуатации

> Это рабочий документ тестовой ветки. Его наличие не означает, что перечисленные проверки выполнены. Не публиковать изменения из staging без проверки на тестовом окружении.

## Правила публикации

1. Любые изменения готовить отдельно от работающей версии; сохранять контрольную точку исходного кода.
2. До публикации проверять HTML, JavaScript, ссылки, мобильную версию и ключевые пользовательские сценарии.
3. Проверять авторизацию *на сервере*, а не по наличию поля ввода пароля в браузере.
4. До обновления динамических данных иметь внешнюю резервную копию и проверенную процедуру восстановления.
5. После публикации проверять сайт с нового устройства без авторизованной сессии, затем проверять административные операции.
6. Успешная сборка кода — не доказательство работоспособности сайта, базы, API и интеграций.

## Ежедневная проверка при обслуживании

- Публичная страница и ключевые ссылки доступны.
- API и операции с динамическим контентом доступны.
- Последняя резервная копия создана без ошибок и защищена от доступа посторонних.
- Срок действия домена и сертификата контролируется.
- Аварии не скрыты за запасной устаревшей страницей.

## Проверки перед передачей заказчику

- [ ] Домен и аккаунты принадлежат заказчику или права оформлены договором.
- [ ] Исходники проекта отделены от остальных заказчиков.
- [ ] Секреты не находятся в публичном клиентском коде или в истории репозитория.
- [ ] Роли доступа и серверная авторизация проверены.
- [ ] Неавторизованный пользователь не может изменять опубликованный контент.
- [ ] Реальная публикация и последующий откат протестированы.
- [ ] Данные сохраняются после перезапуска сервера.
- [ ] Резервная копия восстановлена на отдельном тестовом окружении.
- [ ] Проверена работа на Android, iPhone и компьютере.
- [ ] Клиенту переданы инструкции, границы поддержки и доступы.

## Если сайт недоступен

1. Проверить страницу и API раздельно; исключить временную проблему только своего интернета.
2. Проверить DNS, сертификат, состояние хостинга и логи ошибок.
3. Не удалять данные и не переустанавливать сервер «на всякий случай».
4. Зафиксировать инцидент, сохранить необходимые журналы.
5. При ошибке обновления откатить код на известную исправную версию.
6. При подозрении на утечку ограничить доступ и отозвать затронутые секреты; сохранить доказательства.
7. После восстановления выполнить функциональную проверку, а не ограничиваться статусом 200 OK.

## Резервное копирование

Исходный код GitHub не заменяет резервную копию базы данных, настроек и загруженных файлов.
Для всего, что хранит заявки или историю изменений, требуется независимое защищённое хранение и регулярная проба восстановления.

## Ограничения текущего статуса

Прежде чем выбирать окончательную конфигурацию API и хранения данных, необходимо проверить существующий сервер и экспорт текущих данных. Бесплатный тариф хостинга не означает гарантированной доступности 24/7.
